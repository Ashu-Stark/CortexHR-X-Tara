Summary

CortexHR is a team-built AI hiring platform: candidates upload resumes and an LLM scores each one against the job. This contribution (branch kriti/scoring-reliability) makes that score trustworthy: it finds and fixes four ways a model reply could produce a wrong or fake score, moves the scoring logic into testable functions, adds 21 tests and an evaluation harness.

Tests

Examples of what the 21 tests pin down:

  • The score is always the sum of the categories, even when the model's own total is wrong.
  • String, negative and missing points are handled (converted, or counted as 0).
  • The result always fits the database rule: an integer between 0 and 100.
  • A reply without a breakdown is an error, not a silent zero.
  • The fallback marks the resume for manual review instead of inventing 50.
  • Resume text is capped before it is sent to the model.

Evaluation design

15 fictional resumes for 3 internship roles (backend, frontend, data), each labelled strong / medium / weak for its role. Each is scored twice with the production prompt, model (llama-3.3-70b-versatile) and temperature 0.

QuestionMeasure
RankingFor each pair for the same role with different labels (24 pairs), is the stronger resume scored higher?
ConsistencyDoes the same resume get the same score twice?
ReliabilityHow many replies needed corrections or went to manual review?
The evaluation has not been run yet (it needs an API key), so no results are claimed here. Run npm run eval:scoring and add the numbers from scripts/eval-results.json. Limits: resumes and labels were written by one person and the set is small. It checks that scoring is sensible and stable, not that it is fair across groups of people, which needs a much larger, carefully designed test.

Interview questions

Why was a fallback score of 50 harmful?
It ranked resumes the system failed to read above genuinely weak candidates. Missing data must look missing (null, manual review), not average.
Why move the prompt out verbatim and check it byte-for-byte?
An evaluation is only meaningful if it uses the exact production prompt; any accidental edit would test a different system.
Why clamp each category instead of only the total?
Clamping only the total hides which part was wrong and lets one category crowd out the others; per-category limits keep the breakdown meaningful.
Why not log the raw model reply?
It repeats details from the resume, which is personal data; logs are widely accessible and kept for a long time.
